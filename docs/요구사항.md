# 포트폴리오 웹사이트 요구사항

> 상태: **v1.2 — 주요 결정 확정, 구현 착수 가능** · 최종 수정: 2026-09-20
> 남은 열린 질문은 §11의 2건뿐이며, 둘 다 Phase 1 착수를 막지 않습니다.

---

## 1. 개요

### 1.1 한 줄 정의

프론트엔드 개발자(신입/전환)의 **종합 허브** — 이력·프로젝트·외부 글을 한 곳에 모아 두고, 방문자가 목적에 따라 필요한 정보만 빠르게 꺼내갈 수 있는 사이트.

### 1.2 전제 조건

> ⚠️ **① 보유 프로젝트 콘텐츠가 거의 없고, ② 실무 경력이 없는 상태**에서 시작합니다. 이 두 가지가 설계 전반을 지배합니다.

여기서 따라오는 네 가지 원칙:

1. **사이트 자체가 1번 프로젝트다.** 이 저장소의 성능·접근성·코드 품질이 첫 번째 증거물입니다. 그래서 §5 비기능 요구사항은 "있으면 좋은 것"이 아니라 **필수**입니다.
2. **빈 상태에서도 무너지지 않아야 한다.** 프로젝트 1개, 경력 0줄이어도 레이아웃이 어색해 보이지 않아야 합니다. 3열 그리드에 카드 한 장이 놓인 화면은 없는 것만 못합니다. (FR-P7)
3. **경력이 없으므로 만든 것으로 말한다.** 섹션 순서·분량·서술 방식 전부가 Projects를 향해 정렬됩니다. (§3.2, §4.5)
4. **배포 후 채운다.** 완성 후 배포가 아닙니다. 그릇을 먼저 만들고 내용은 계속 들어갑니다.

### 1.3 확정된 결정 (Decision Record)

| ID | 결정 | 근거 | 재검토 조건 |
|---|---|---|---|
| **D1** | **라우터 없는 단일 페이지.** 프로젝트 상세는 같은 페이지 내 확장(아코디언/모달) | 라우터를 정당화하던 두 근거가 모두 사라짐 — ①블로그는 외부로(D2) ②프로젝트가 아직 없어 상세 페이지를 채울 내용이 없음. 없는 것을 위해 미리 구조를 짓지 않음. GitHub Pages(D5)에서 SPA 라우팅이 까다롭다는 점도 이 결정을 지지함 | 프로젝트가 6개 이상이 되거나, 개별 프로젝트를 **단독 URL로 공유**할 필요가 생길 때 → React Router 도입 (`slug`를 URL로 승격) |
| **D2** | **자체 블로그를 만들지 않는다.** 외부 블로그 링크로 대체 | 공개 가능한 글이 5편 미만. 빈 블로그는 "관리되지 않는 사이트"라는 역신호 | 글이 5편 이상 쌓이고 이관 의사가 생길 때 |
| **D3** | **CSS Modules + CSS 커스텀 프로퍼티** | 런타임 의존성 0, 다크모드 토큰화에 자연스러움, 프론트엔드 지원자로서 CSS 역량 신호 | 없음 |
| **D4** | Vite + React 19 + TypeScript (현 스캐폴드 유지) | 이미 구성됨. 전환 이득 없음 | 없음 |
| **D5** | **GitHub Pages + GitHub Actions 자동 배포** | 무료, 저장소와 일체, 정적 사이트만 필요한 이번 구성에 충분. §5.7의 제약을 수용하는 조건으로 채택 | 서버 함수나 리다이렉트가 필요해질 때 |
| **D6** | **Vitest + Testing Library, 핵심 테스트만** | 사이트 자체가 1번 프로젝트이므로(원칙 1) 테스트 설정의 부재가 약점으로 읽힘. 커버리지 목표는 세우지 않음 | 없음 |
| **D7** | **Experience 섹션을 `Education & Activities`로 대체** | 실무 경력 없음. 빈 경력 섹션은 약점을 강조할 뿐 | 실무 경력이 생겼을 때 |
| **D8** | **Skills에 숙련도 라벨을 붙이지 않는다.** 카테고리별 나열만 | 신입 단계에서 `주력`/`실무 경험` 같은 라벨은 근거를 대기 어렵고, 면접에서 역공의 빌미가 됨. 숙련도는 **Projects의 기술 태그와 서술이 증명**하게 함 | 경력이 쌓여 기술 간 깊이 차이가 뚜렷해질 때 |

### 1.4 성공 기준

| # | 성공 기준 | 측정 방법 |
|---|---|---|
| S1 | 처음 방문한 채용담당자가 **5분 안에** "이 사람이 뭘 할 수 있는지" 파악 | 지인 3명에게 5분 타이머 후 구두 요약 요청 |
| S2 | 사이트 자체가 프론트엔드 실력의 **증거물**로 기능 | Lighthouse 4개 지표 95+ (§5) |
| S3 | 이력서·지원서·SNS에서 **링크 하나로** 대체 가능 | URL 하나로 모든 요청 정보 커버되는지 체크 |
| S4 | 콘텐츠 추가가 **부담되지 않음** (프로젝트 1개 추가 = 30분 이내) | 데이터 파일 1곳 수정으로 끝나는지 (§6) |
| S5 | **배포 후에도 계속 갱신됨** | 3개월 뒤 마지막 커밋이 3개월 전이 아닐 것 |

> S4·S5가 핵심입니다. 대부분의 개인 포트폴리오는 **만들고 나서 방치**되어 죽습니다. 콘텐츠가 부족한 상태에서 출발하는 이번 경우 특히, 유지 비용이 1급 요구사항입니다.

## 2. 타깃 사용자

### P1. 채용담당자 / 기술 면접관 (최우선)

- **맥락**: 지원서에 붙은 링크를 클릭. 체류 시간 **2~5분**. 모바일일 수도 있음.
- **원하는 것**: 기술 스택 / 대표 프로젝트에서 *본인이 실제로 한 일* / 코드를 볼 수 있는 링크.
- **신입 지원자를 볼 때의 추가 관심사**: 혼자 끝까지 완성해 본 적이 있는가, 기술 선택에 이유를 댈 수 있는가, 코드에 일관성이 있는가. → §4.5의 서술 항목이 이를 겨냥합니다.
- **이탈 유발 요인**: 로딩 중 빈 화면, 무엇을 클릭해야 할지 모르겠는 첫 화면, 스크롤 3번 해도 정보가 안 나오는 장식용 인트로.

### P2. 프리랜스 의뢰 검토자

- **맥락**: 추천이나 검색으로 유입. "이 사람에게 맡겨도 되나"를 판단.
- **원하는 것**: 비슷한 작업 사례, 작업 범위·결과, **연락 수단**.
- **P1과의 차이**: 내부 구현보다 *결과물과 신뢰 신호*(실제 동작하는 링크, 기간, 역할)를 봄.

### P3. 동료 개발자 (부차적)

- 자체 블로그를 두지 않으므로(D2) 글을 통한 직접 유입은 당분간 없습니다. GitHub에서 넘어와 About을 훑는 정도의 방문자입니다.
- **함의**: 외부 블로그 링크는 "글이 쌓이는 곳"으로 안내하는 역할만 합니다.

### 2.1 우선순위 선언

충돌 시 **P1 > P2 > P3**.

## 3. 정보 구조 (IA)

### 3.1 페이지 구성

**단일 경로 하나.** (D1)

```
/    Hero → About → Skills → Projects → Education & Activities → Contact
```

> 프로젝트 상세는 같은 페이지 안에서 펼쳐집니다(FR-P4). 데이터 모델에 `slug`를 미리 넣어, 훗날 라우터 도입 시 그대로 URL이 되도록 합니다.

### 3.2 섹션 순서와 근거

| 순서 | 섹션 | 존재 이유 (P1 기준) |
|---|---|---|
| 1 | **Hero** | 이름·직무·한 줄 정의. 3초 안에 "누구인지" 전달 |
| 2 | **About** | 강점과 전환 동기. 인간적 맥락 |
| 3 | **Skills** | 기술 스택 **스캔** 구간. 면접관의 키워드 매칭 |
| 4 | **Projects** | **가장 긴 체류 구간이자 이 사이트의 본체** |
| 5 | **Education & Activities** | 학습 이력, 부트캠프, 스터디, 수상 등 (D7) |
| 6 | **Contact** | 이메일·GitHub·외부 블로그 |

> 경력이 없으므로(원칙 3) Projects가 Education보다 앞섭니다. 학력이 아니라 만든 것으로 판단받는 구성입니다.

### 3.3 전역 요소

- **상단 네비게이션**: 섹션 앵커 링크. 스크롤 시 현재 섹션 하이라이트. 모바일은 햄버거 또는 하단 고정 바.
- **푸터**: 저작권, **이 사이트의 소스 저장소 링크**. GitHub Pages 무료 플랜에서는 어차피 저장소가 공개되므로(§5.7), 이를 약점이 아니라 신호로 활용합니다.

## 4. 기능 요구사항

### 4.1 Hero

- **FR-H1** 이름, 직무(예: "Frontend Engineer"), 한 줄 소개를 표시한다.
- **FR-H2** 주요 CTA를 최대 2개 노출한다 (예: `프로젝트 보기`, `GitHub`). 3개 이상은 선택 마비를 유발하므로 금지.
- **FR-H3** 첫 화면에서 **스크롤 없이** 이름·직무·CTA가 모두 보인다. 모바일 375×667 기준 포함.
- **FR-H4** 애니메이션이 있더라도 텍스트는 JS 실행 여부와 무관하게 즉시 렌더된다.

### 4.2 About

- **FR-A1** 2~4문단 또는 불릿으로 강점·관심사를 기술한다.
- **FR-A2** 프로필 이미지는 선택. 넣는다면 WebP/AVIF + 명시적 `width`/`height`로 레이아웃 시프트를 방지한다.
- **FR-A3** **전환 동기와 방향성**을 한 문단으로 포함한다. 신입·전환 지원자에게 P1이 궁금해하는 것은 "왜 이 일을 하려 하는가"와 "얼마나 지속할 사람인가"입니다. 사과조("아직 부족하지만")가 아니라 **현재형 서술**로 씁니다.

### 4.3 Skills

- **FR-S1** 기술을 **카테고리로 묶어** 표시한다 (예: Language / Framework / Tooling).
- **FR-S2** **숙련도 표기(% 게이지, 별점, 상중하 라벨)를 쓰지 않는다.** (D8) 카테고리별 나열만 하고, 깊이는 Projects가 증명한다.
- **FR-S3** 아이콘을 쓸 경우 텍스트 라벨을 반드시 병기한다 (접근성 + 스캔 용이성).
- **FR-S4** **면접에서 질문받을 각오가 된 것만** 올린다. 목록을 길게 늘여 부풀리지 않는다. 신입 이력서에서 20개짜리 기술 나열은 오히려 감점 요인입니다.

### 4.4 Projects

이 사이트의 **본체**이자, 현재 **가장 비어 있는 섹션**입니다.

- **FR-P1** 카드 목록으로 표시한다. 카드에는 썸네일, 제목, 한 줄 설명, 기술 태그, 기간이 포함된다.
- **FR-P2** 각 프로젝트는 다음 네 가지를 명시한다:
  - **문제** — 무엇을 왜 만들었는가
  - **역할** — 팀 프로젝트라면 *본인이 한 부분*을 분명히
  - **기술적 선택과 이유** — "React를 썼다"가 아니라 "왜 그렇게 했는가". **경력이 없을수록 이 항목이 결정적입니다.** 판단 과정을 보여주는 것이 경력을 대신합니다
  - **결과** — 배포 여부, 지표, 배운 점
- **FR-P3** 각 프로젝트는 **라이브 데모 링크**와 **소스 코드 링크**를 가진다. 없다면 그 사실을 명시한다.
- **FR-P4** 상세는 같은 페이지에서 펼쳐진다(아코디언 또는 모달). 키보드로 조작 가능해야 하며, 모달이라면 포커스 트랩과 `Esc` 닫기를 구현한다.
- **FR-P5** ~~태그 필터~~ — **범위 밖.** 프로젝트 6개 이상이 되기 전까지 도입하지 않는다.
- **FR-P6** 썸네일 부재 시 깨지지 않는 **플레이스홀더**를 제공한다.
- **FR-P7** **프로젝트 수가 1~2개여도 레이아웃이 자연스러워야 한다.** 고정 3열 그리드 대신, 개수에 따라 자연스럽게 배치되는 방식(적은 수에서는 가로로 넓은 카드 1열)을 사용한다.
- **FR-P8** 이 포트폴리오 사이트 자체를 **첫 프로젝트 항목으로 등재**한다. 요구사항 수립 → 설계 → 성능·접근성 목표 달성 과정을 FR-P2 형식으로 서술한다. *(빈칸 메우기가 아니라 실제로 보여줄 값이 있습니다 — 이 문서가 그 증거입니다.)*

### 4.5 Education & Activities

- **FR-E1** 학력, 부트캠프·교육과정, 스터디, 수상, 자격 등을 역순으로 표시한다.
- **FR-E2** 항목별로 기간과 **무엇을 했는지 1~2줄**을 덧붙인다. 기관명만 나열하지 않는다.
- **FR-E3** 내용이 2건 미만이면 **섹션 자체를 렌더하지 않는다.** 제목만 남은 빈 섹션을 만들지 않는다.
- **FR-E4** 훗날 실무 경력이 생기면 이 섹션 위에 `Experience`를 추가한다 (D7의 재검토 조건).

### 4.6 Contact & Links

- **FR-C1** 이메일 주소, GitHub, **외부 블로그** 링크를 제공한다. (D2)
- **FR-C2** 이메일은 클릭 시 복사되거나 `mailto:`로 열린다. 봇 수집 방지를 위한 최소한의 난독화를 고려한다.
- **FR-C3** 문의 폼은 Phase 1 범위 밖. 필요해지면 Formspree 등으로 30분이면 추가된다.
- **FR-C4** 외부 블로그 링크에는 **그곳에 무엇이 있는지** 한 줄을 덧붙인다 (예: "React와 성능 최적화에 대해 씁니다"). 맨 아이콘만 있으면 클릭되지 않습니다.

### 4.7 공통 UX

- **FR-X1** 모든 외부 링크는 새 탭(`target="_blank" rel="noopener noreferrer"`)으로 연다.
- **FR-X2** 다크 모드를 지원한다. 기본값은 `prefers-color-scheme`을 따르고, 수동 토글 시 `localStorage`에 기억한다.
- **FR-X3** `prefers-reduced-motion` 사용자에게는 모든 애니메이션을 비활성화한다.
- **FR-X4** 앵커 네비게이션은 키보드로 접근 가능하며, 본문으로 건너뛰는 `Skip to content` 링크를 제공한다.

## 5. 비기능 요구사항

> 원칙 1에 따라 **협상 대상이 아닙니다.** 보여줄 프로젝트가 적을수록 사이트 자체의 완성도가 더 많은 것을 말합니다.

### 5.1 성능

- **NFR-PF1** Lighthouse Performance **≥ 95** (모바일 기준, 배포 환경 측정).
- **NFR-PF2** LCP < 2.5s, CLS < 0.1, INP < 200ms.
- **NFR-PF3** 초기 JS 번들 **gzip 후 100KB 이하**. 라이브러리 추가 시 이 예산을 기준으로 판단한다.
- **NFR-PF4** 이미지는 WebP/AVIF, `loading="lazy"`(첫 화면 제외), 명시적 크기 지정.
- **NFR-PF5** 웹폰트는 최대 2종. `font-display: swap` + subset 적용.

### 5.2 접근성

- **NFR-A11Y1** Lighthouse Accessibility **≥ 95**.
- **NFR-A11Y2** 시맨틱 HTML (`<header> <nav> <main> <section> <article> <footer>`), 헤딩 레벨 순서 준수.
- **NFR-A11Y3** 키보드만으로 전체 탐색 가능. 포커스 링이 **보인다** (`outline: none` 금지, `:focus-visible`로 교체).
- **NFR-A11Y4** 본문 텍스트 명도 대비 **4.5:1 이상**, 다크·라이트 양쪽에서.
- **NFR-A11Y5** 모든 이미지에 의미 있는 `alt` (장식용은 `alt=""`).

### 5.3 반응형

- **NFR-R1** 지원 폭 **320px ~ 1920px**. 가로 스크롤 없음.
- **NFR-R2** 브레이크포인트: 모바일 `~767px` / 태블릿 `768~1023px` / 데스크톱 `1024px~`.
- **NFR-R3** **모바일 퍼스트**로 작성한다.
- **NFR-R4** 터치 타깃 최소 44×44px.

### 5.4 SEO / 공유

- **NFR-SEO1** 본인 이름 검색 시 노출을 목표로 한다. `<title>`, `meta description`, 시맨틱 마크업.
- **NFR-SEO2** OG / Twitter 카드 이미지를 제공한다.
- **NFR-SEO3** `robots.txt`, `sitemap.xml` 제공.
- **NFR-SEO4** JSON-LD `Person` 스키마를 `index.html`에 **정적으로** 삽입한다. CSR 환경에서도 크롤러가 읽는 안전망.
- **NFR-SEO5** 페이지가 하나뿐이므로 CSR로 인한 SEO 손실은 제한적이다. 다만 Hero의 이름·직무 텍스트는 `index.html`에 정적으로 두는 방안을 검토한다.

### 5.5 브라우저 지원

- **NFR-BR1** 최신 2개 버전의 Chrome / Edge / Safari / Firefox. IE 미지원.
- **NFR-BR2** JS 비활성화 환경은 지원 대상이 아니다.

### 5.6 유지보수성 / 코드 품질

- **NFR-M1** 콘텐츠와 컴포넌트를 분리한다. 프로젝트 추가 = **데이터 파일 1곳 수정** (S4).
- **NFR-M2** TypeScript strict. `any` 사용 시 주석으로 사유를 남긴다.
- **NFR-M3** `npm run build`와 `npm run lint`가 무경고로 통과해야 한다.
- **NFR-M4** 컴포넌트는 `src/components/<Name>/`에 `.tsx` + `.module.css`를 함께 둔다. (D3)
- **NFR-M5** **테스트**(D6): Vitest + Testing Library + jsdom. 최소 대상은 ①다크 모드 토글 동작과 `localStorage` 반영 ②데이터 배열이 비었을 때 섹션이 깨지지 않음(FR-P7·FR-E3의 회귀 방지) ③주요 섹션의 헤딩 구조. `npm test`로 실행되며 CI에서 배포 전 통과해야 한다.
- **NFR-M6** 저장소가 공개되므로 코드는 **읽힐 것을 전제로** 작성한다. 커밋 메시지, 디렉터리 구조, README도 평가 대상입니다.

### 5.7 배포 제약 (GitHub Pages) — D5의 대가

무료 정적 호스팅을 택한 대신, 다음 제약을 **설계에 미리 반영**해야 합니다.

- **NFR-D1 경로(base) 문제.** 저장소 페이지(`user.github.io/repo/`)로 배포하면 사이트가 하위 경로에 놓입니다. `vite.config.ts`의 `base`를 설정해야 하고, **`public/` 자산을 `/icons.svg`처럼 절대 경로로 참조하면 깨집니다.** `import.meta.env.BASE_URL`을 경유하거나 `src/assets/`로 옮겨 import 방식으로 참조합니다.
  > **권고**: 저장소 이름을 **`<username>.github.io`** 로 만들어 **루트 경로**에 배포합니다. `base` 설정이 불필요해지고 주소도 `yjw1555.github.io`로 짧아집니다. 커스텀 도메인은 나중에 CNAME으로 얹으면 됩니다.
- **NFR-D2 서버 사이드 기능 없음.** 리다이렉트, 환경변수 주입, API 프록시가 불가능합니다. 단일 페이지(D1)이므로 SPA 404 리라이트 문제는 발생하지 않습니다 — **D1의 부수적 이득**입니다.
- **NFR-D3 저장소 공개 필요.** 무료 플랜에서 Pages는 공개 저장소에서만 동작합니다. **API 키·개인정보·이력서 원본 등을 커밋하지 않습니다.** 이메일 노출 방식도 이를 전제로 결정합니다(FR-C2).
- **NFR-D4 자동 배포.** GitHub Actions 워크플로로 `main` 푸시 시 `build → test → deploy`가 자동 실행됩니다. 수동 업로드는 하지 않습니다.
- **NFR-D5 커스텀 도메인은 보류.** 필요해지면 도메인 구입 후 CNAME 추가만으로 전환되며, 전환 비용이 낮으므로 지금 결정하지 않습니다.

## 6. 콘텐츠 데이터 모델

> 데이터를 먼저 정하고 컴포넌트를 그 형태에 맞춥니다. 이 구조가 확정되면 **UI 작업과 콘텐츠 작성을 병렬로** 진행할 수 있습니다 — 콘텐츠가 부족한 지금 특히 중요합니다.

```ts
// src/data/types.ts (초안)

interface SkillCategory {
  category: string        // 'Frontend'
  items: string[]         // ['React', 'TypeScript']  — 숙련도 라벨 없음 (D8)
}

interface Project {
  slug: string            // 키로 사용. 훗날 URL로 승격 (D1)
  title: string
  tagline: string         // 카드용 한 줄
  period: { start: string; end: string | null }
  role: string            // FR-P2: 본인이 한 일
  problem: string
  decisions: string[]     // 기술적 선택과 이유 — 신입에게 가장 중요한 필드
  outcome: string[]
  stack: string[]
  thumbnail?: string
  links: {
    demo?: string
    repo?: string
    article?: string      // 외부 블로그에 쓴 관련 글
  }
  featured: boolean
}

interface EducationItem {
  title: string           // '○○ 부트캠프 프론트엔드 과정'
  organization: string
  start: string           // '2025-03'
  end: string | null
  highlights: string[]    // FR-E2: 무엇을 했는지
}

interface ExternalLink {
  label: string           // 'Blog'
  url: string
  description?: string    // FR-C4
}
```

## 7. 디자인 방향

### 7.1 무드

- **DS1 톤**: **절제된 미니멀 + 다크·테크 무드.** 콘텐츠가 주인공, 장식은 조연이되 배색·타이포는 "만들 줄 아는 개발자"의 인상을 겨냥한다. 스위스/그리드 계열의 타이포그래피 위계와 여백(§DS7)으로 절제를 유지하면서, 액센트 컬러(§DS2)와 다크 팔레트(§DS8)로 테크 성향을 드러낸다.
- **DS1a 레퍼런스 축**: Linear, Vercel류의 "타이포 위계 + 그리드"가 1차 참고축. 화려한 그라디언트·글래스모피즘·3D는 지양(§8 범위 밖, NFR-PF1과도 상충).

### 7.2 컬러 (DS2)

뉴트럴 기반 + **액센트 1색(블루/인디고 계열)**. 아래 값은 WCAG 2.x 상대 휘도 공식으로 대비를 계산해 NFR-A11Y4(4.5:1) 기준으로 **검증 완료**한 값이다.

| 토큰 | 라이트 | 다크 | 용도 |
|---|---|---|---|
| `--color-bg` | `#FFFFFF` | `#0B0E14` | 페이지 배경 |
| `--color-surface` | `#F7F8FA` | `#12151C` | 카드·섹션 배경 |
| `--color-text` | `#14161A` | `#E8EAED` | 본문 텍스트 |
| `--color-text-muted` | `#475569` | `#9AA1AC` | 보조 텍스트, 캡션 |
| `--color-border` | `#E2E4E9` | `#262B33` | 구분선, 카드 테두리 |
| `--color-accent` | `#4F46E5` | `#818CF8` | 링크, 강조 텍스트, 포커스 링 |
| `--color-accent-bg` | `#4F46E5` | `#5A5DE8` | 버튼 등 채워진 액센트 배경 (텍스트는 `#FFFFFF`) |

- 액센트는 CTA 버튼, 링크, 포커스 링(NFR-A11Y3), 활성 네비게이션 표시 등 **강조가 필요한 지점에만** 쓴다. 배경 전체를 물들이지 않는다(DS1의 절제 원칙 유지).
- 다크 배경은 순수 검정(`#000`)이 아니라 미세하게 푸른 톤을 섞어(`#0B0E14`) "테크" 인상을 주되 눈부심을 낮춘다.
- **대비 검증 결과** (배경 대비 텍스트, 4.5:1 기준):
  - 라이트 `--color-text` on `--color-bg`: **18.1:1**
  - 라이트 `--color-text-muted` on `--color-bg`: **7.6:1**
  - 라이트 `--color-accent` on `--color-bg`: **6.3:1**
  - 다크 `--color-text` on `--color-bg`: **16.0:1**
  - 다크 `--color-text-muted` on `--color-bg`: **7.4:1**
  - 다크 `--color-accent` on `--color-bg`: **6.5:1**
  - `--color-accent-bg` + 흰색 텍스트: 라이트 **6.3:1** / 다크 **5.0:1**
  - ⚠️ **수정 이력**: 원래 다크 `--color-accent-bg` 후보였던 `#6366F1`(Tailwind Indigo-500)은 흰색 텍스트와 대비 **4.47:1**로 기준(4.5:1) 미달이었다. 동일 색상(-hue) 유지하며 살짝 어둡게 조정한 `#5A5DE8`로 교체해 5.0:1을 확보했다 (`--color-bg` 대비 3.8:1로 버튼-배경 구분도 유지).
  - 위 수치는 sRGB 헥스값 기준 계산이며, 실제 렌더링(서브픽셀, 안티에일리어싱)에서도 Lighthouse/axe로 재확인한다.

### 7.3 타이포그래피 (DS3)

- **폰트**: **Pretendard 단일 사용** (한글·영문·숫자 모두). `font-family: 'Pretendard Variable', Pretendard, -apple-system, BlinkMacSystemFont, system-ui, Roboto, 'Helvetica Neue', 'Segoe UI', sans-serif;` 폰트 1종만 쓰므로 NFR-PF5(웹폰트 최대 2종)를 여유 있게 충족한다.
- **크기 스케일**: `--font-size-sm: 14px`(보조 텍스트, 최소 사용) · `--font-size-base: 16px`(본문) · `--font-size-lg: 20px`(리드 문단) · `--font-size-xl: 28px`(섹션 제목 `h2`) · `--font-size-2xl: 40px`(Hero 이름, `h1`).
- **행간**: 본문 1.6 이상, 헤딩 1.2~1.3.
- **한 줄 길이**: 최대 약 70자.
- **굵기**: Regular(400) / Medium(500, 강조 라벨) / SemiBold(600, 헤딩) 3단계만 사용. 과도한 굵기 종류는 위계를 흐린다.

### 7.4 간격 · 레이아웃 (DS4)

- **간격 스케일**: 4 또는 8px 배수. 토큰명 예: `--space-1 … --space-8`.
- **본문 컨테이너 최대 너비**: **1200px**. 1024px+ 데스크톱(NFR-R2)에서 한 줄 텍스트가 과도하게 길어지지 않도록 하고, DS7(여백 전략)과 맞물려 여백을 넉넉히 확보한다.

### 7.5 컴포넌트 형태 — 모서리 · 그림자 (DS9)

카드·버튼·입력창 등은 **둥근 모서리 + 은은한 그림자**로 통일한다.

| 토큰 | 값 | 용도 |
|---|---|---|
| `--radius-sm` | 6px | 입력창, 태그, 작은 버튼 |
| `--radius-md` | 10px | 버튼, 카드 내부 요소 |
| `--radius-lg` | 16px | 프로젝트 카드, 섹션 컨테이너 |
| `--shadow-sm` (라이트) | `0 1px 2px rgba(15,17,21,.06)` | 기본 카드 |
| `--shadow-md` (라이트) | `0 4px 12px rgba(15,17,21,.08)` | hover, 모달 |
| `--shadow-sm` (다크) | `0 0 0 1px rgba(255,255,255,.04), 0 1px 2px rgba(0,0,0,.4)` | 기본 카드 |
| `--shadow-md` (다크) | `0 0 0 1px rgba(255,255,255,.06), 0 8px 24px rgba(0,0,0,.5)` | hover, 모달 |

> 다크 배경에서는 검정 그림자가 거의 보이지 않으므로, 그림자 대신 **1px 반투명 흰색 테두리**를 함께 써서 표면 구분을 만든다.

### 7.6 아이콘 (DS10)

- **Lucide** 아이콘 세트를 사용한다. 트리셰이킹되는 SVG 기반이라 번들 예산(NFR-PF3)에 미치는 영향이 미미하고, 스트로크 기반 선화가 다크·테크 무드(DS1)와 잘 어울린다.
- 스트로크 두께는 기본값(1.5~2px) 유지, 크기는 16/20/24px 중 문맥에 맞게 선택.
- 아이콘 단독 사용 금지 — 항상 텍스트 라벨을 병기한다(FR-S3과 동일 원칙을 전역 적용).

### 7.7 이미지 · 썸네일 처리 (DS11)

- 프로젝트 카드·썸네일 이미지는 **별도 필터 처리 없이** 원본 그대로 노출한다. 카드 모서리(`--radius-lg`)로만 구분하고, 흑백·듀오톤 등의 가공은 하지 않는다.
- 썸네일이 없는 경우의 플레이스홀더(FR-P6)는 `--color-surface` 배경 위에 `--color-border` 테두리 + 중앙 아이콘(Lucide `image` 또는 프로젝트 이니셜) 정도의 최소 구성으로 한다.

### 7.8 모션 (DS5)

스크롤 진입 시 페이드·슬라이드 정도. 200~400ms, ease-out. FR-X3(`prefers-reduced-motion`) 준수.

### 7.9 다크 모드 정책 (DS8)

- 기본값은 **시스템 설정(`prefers-color-scheme`)을 따른다** (FR-X2 유지). 무드가 "다크·테크"라고 해서 다크를 강제 기본값으로 만들지는 않는다 — 라이트 시스템 사용자에게 원치 않는 전환을 강요하지 않는 접근성·사용자 선호 존중 원칙(NFR-A11Y) 때문.
- 대신 **라이트 팔레트를 다크의 축소판으로 두지 않고, §7.2의 다크 토큰 값을 라이트만큼 공들여 설계**한다 — 이 사이트를 처음 여는 인상(수동 토글 시 포함)이 무드를 대표하는 경우가 많기 때문.

### 7.10 구현 (DS6)

**CSS Modules + CSS 커스텀 프로퍼티** (D3). §7.2·§7.3·§7.4·§7.5의 토큰은 `src/styles/tokens.css`에 전역 정의하고, 컴포넌트는 `*.module.css`에서 토큰만 참조한다. 하드코딩된 색상값·radius·shadow 값 금지.

### 7.11 여백 전략 (DS7)

콘텐츠가 적을 때는 **여백을 넉넉히** 쓰는 편이 빈 공간을 억지로 채우는 것보다 낫습니다. 절제된 디자인은 콘텐츠 부족을 의도된 미니멀리즘으로 보이게 합니다.

## 9. 프로젝트 콘텐츠 확보 계획

> **이것이 실질적인 주공정(critical path)입니다.** 사이트 구현은 며칠이면 끝나지만, 채울 내용이 없으면 포트폴리오로 기능하지 않습니다.

### 9.1 최소 목표

**"의미 있게 서술할 수 있는 프로젝트 3개."** 3개가 인상의 손익분기점입니다. 1개는 우연, 2개는 취미, 3개부터 패턴으로 읽힙니다.

### 9.2 확보 현황

| 순번 | 후보 | 상태 |
|---|---|---|
| 1 | **이 포트폴리오 사이트** | 진행 중. FR-P8로 자동 확보 |
| 2 | **실사용자가 있는 소규모 웹서비스** | 방향 확정, **아이템 미정** (§11 Q10) |
| 3 | 미정 | 2번 진행하며 결정 |

### 9.3 선정 기준

- **완결 가능한 크기** — 2~3주 안에 배포까지. 미완성 대작보다 완성된 소품이 낫습니다.
- **살아 있는 링크** — 실제로 열리는 URL이 있어야 합니다 (FR-P3). 이것 하나로 신뢰도가 갈립니다.
- **설명할 기술적 판단이 있을 것** — 튜토리얼 복제는 FR-P2의 `decisions`를 쓸 수 없습니다.
- **서로 다른 면을 보여줄 것** — 비슷한 것 3개보다, 예컨대 *①사이트(설계·성능) ②실사용자 서비스(운영) ③다른 축*이 폭을 보여줍니다.

### 9.4 "실사용자가 있는 서비스"를 택했을 때의 추가 고려사항

가장 강한 신뢰 신호이지만(선택 근거), 다른 유형에 없는 부담이 따라옵니다. **아이템 선정 단계에서 미리 따져야 합니다.**

- **운영 비용** — 이 포트폴리오와 달리 정적 호스팅만으로는 부족할 수 있습니다. 데이터 저장이 필요하면 무료 티어(Supabase, Cloudflare D1 등) 범위 안에서 설계합니다. **포트폴리오용 프로젝트가 매달 돈이 나가면 결국 내려갑니다.**
- **개인정보** — 사용자 데이터를 받는 순간 책임이 생깁니다. 로그인·개인정보 수집이 없는 형태가 안전하고, 만들기도 빠릅니다.
- **"사용자"의 현실적 정의** — 수천 명을 목표할 필요가 없습니다. **내가 매일 쓰는 도구**, 혹은 특정 소모임이 쓰는 것으로 충분합니다. FR-P2의 `outcome`에 "주 3회 이상 사용하는 이용자 N명" 정도만 써도 튜토리얼 복제와는 완전히 다른 층위가 됩니다.
- **회수 가능한 지표를 처음부터 심어둘 것** — 방문/사용 횟수를 나중에 복원하기는 어렵습니다. 첫 배포 때부터 간단한 집계를 넣어두면 나중에 `outcome`에 쓸 숫자가 생깁니다.

## 10. 단계별 계획

각 Phase의 끝은 **배포 가능한 상태**입니다.

### Phase 0 — 기반 (반나절)

- **git 저장소 초기화** *(현재 미초기화 상태)* 및 GitHub 저장소 생성 — 이름은 NFR-D1 권고에 따라 결정
- GitHub Actions 배포 워크플로 작성, **빈 페이지 상태로 1회 배포해 파이프라인을 먼저 검증** (나중에 디버깅하지 않기 위해)
- Vitest + Testing Library 설정 (D6)
- 디자인 토큰(`tokens.css`), 전역 리셋, 다크 모드 변수 체계
- 레이아웃 셸(헤더 / main / 푸터) + 다크 모드 토글
- 데이터 모델(§6) 타입 정의

### Phase 1 — 랜딩 골격과 첫 공개 (2~3일)

- Hero / About / Skills / Contact — **콘텐츠가 적어도 채울 수 있는 섹션들**
- Projects 섹션 (FR-P7의 소량 대응 레이아웃 포함), 항목은 FR-P8의 사이트 자체 1건
- Education & Activities (내용이 2건 이상일 때만 — FR-E3)
- 반응형 + 접근성 통과, Lighthouse 측정, 핵심 테스트 작성
- **공개 배포.** 이 시점부터 링크를 남에게 보낼 수 있어야 함

### Phase 2 — 콘텐츠 채우기 (지속, §9와 병행)

- 2번 프로젝트 아이템 확정 및 제작 → 등재
- 프로젝트 상세 확장 UI(FR-P4) 구현
- OG 이미지, sitemap, robots.txt, JSON-LD
- 3번 프로젝트

### Phase 3 — 다듬기 (상시)

- 성능 튜닝, 모션 디테일, 영문 버전
- 프로젝트 6개 도달 시 D1·FR-P5 재검토
- 실무 경력 발생 시 D7 재검토

## 11. 열린 질문

> 두 건 모두 **Phase 0~1 착수를 막지 않습니다.** 구현과 병행해 결정할 수 있습니다.

### Q10. 2번 프로젝트의 구체적 아이템 — 가장 중요

방향은 "실사용자가 있는 소규모 웹서비스"로 정해졌고, §9.3·§9.4가 필터입니다. 남은 것은 **무엇을 만들 것인가**입니다.
실마리가 될 질문들:

- 평소 **직접 겪은 불편**이 있는가? (가장 좋은 출발점입니다. 본인이 첫 사용자가 되면 "실사용자" 조건이 즉시 충족됩니다)
- 속한 모임·스터디·동호회에서 **엑셀이나 카톡으로 억지로 하고 있는 일**이 있는가?
- 관심 있는 도메인(운동, 요리, 게임, 가계부, 독서…)이 있는가?

> Phase 1이 끝날 무렵 별도로 브레인스토밍하는 것을 제안합니다. 지금 억지로 정하면 동기 없는 아이템이 나오고, 동기 없는 프로젝트는 완성되지 않습니다.

### Q11. GitHub 저장소 이름

NFR-D1의 권고(`<username>.github.io`)를 따를지, 현재 폴더명대로 `my-portfolio` 저장소로 하위 경로 배포할지. 전자를 권합니다 — `base` 설정과 자산 경로 문제가 통째로 사라집니다.
